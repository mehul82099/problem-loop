# Azure SDK for .NET: the management-plane generator emits operation methods that never dispose their HttpMessage

**Source:** https://github.com/Azure/azure-sdk-for-net/issues/64463 (opened 2026-11-03 UTC, open, filed by an Azure SDK team member, routed by automation to the generator owners)

## The problem

Code generated by the Azure management-plane .NET generator (`eng/packages/http-client-csharp-mgmt`) declares `HttpMessage message = ...` with a plain declaration - no `using` - sends it, reads the response, and returns. Nothing downstream takes ownership: neither the generated pipeline helpers nor `HttpPipeline.Send`/`SendAsync` dispose the message. The reporter traced the full ownership chain to show what leaks: `HttpMessage.Dispose()` would dispose the request, the property bag and the response; the default transport request's `Dispose()` returns pooled header storage and disposes request content; model-backed request content releases serialized pooled buffers. All of that is abandoned on every generated non-LRO call - success and failure paths alike, since the catch block only records diagnostics and rethrows.

The concrete sighting is in the generated Azure.ResourceManager.AIInfraOptimization beta (introduced by the still-open AutoPR #64312): both `RecommendVmSkuAsync` and `RecommendVmSku` are affected. Verified directly at the commit the issue cites - lines 76 and 125 of the generated `MockableAIInfraOptimizationSubscriptionResource.cs` both declare the message without disposal, exactly as reported. Because the fix belongs in the generator's method provider, every management library it emits shares the defect, which is why the reporter frames it as a generator-level ownership issue, not a per-package customization.

## Why it matters

Management SDKs are called in loops - inventory sweeps, policy evaluation, cost tooling - so a per-call leak of pooled buffers and undisposed responses compounds into memory pressure in exactly the long-running automation these libraries target. The reporter also flags the subtlety a correct fix must respect: LRO and streaming operations have different message lifetimes, so a blanket `using` in a shared helper could dispose messages still in flight; the fix needs per-operation-shape ownership plus regression coverage for sync, async, and failure cleanup.

## Caveats

- Open, no fix merged yet; labeling/routing so far is the repo's automated triage (attributed here as tooling, not maintainer review).
- The reporter is a team member writing from code review of the affected generated PR; the ownership-chain claims were spot-verified at the cited commit for the two named methods, not audited across the whole generator output.
- This finding does not propose a specific patch beyond what the reporter already outlines.
