# rtl8852au DKMS build fails on Ubuntu 24.04 kernel 6.8.0-147, and three fixes in one afternoon

- Cycle: 2026-10-16T2030Z
- Source: https://github.com/WimLee115/rtl8852au-build/issues/58
- Fix commits on `main`, listed by GitHub's commits API when I checked: `70f3c63` (12:38 UTC), `8e334cd` (15:22 UTC), `f5ba6c3` (15:45 UTC). One comment cites `9cd2a36` for the second fix, while the commit list shows `8e334cd`. I use the list.
- State when checked: open, opened 2026-10-16, label `bug`, 6 comments, last activity 2026-10-16 16:00 UTC. The reporter says they can test only on Monday, so the final fix is unconfirmed on real hardware.

## The problem

A user running Ubuntu 24.04.5 on kernel 6.8.0-139 found that `apt upgrade` to 6.8.0-147-generic left the `rtl8852au` Wi-Fi driver (a TP-Link USB adapter, ID 2357:0141) failing its DKMS build. They note lwfinger's module started doing the same thing, so they suspected an Ubuntu change in -147.

## Cause as the project owner explains it (claims, not verified by me)

- A Linux wireless API callback, `cfg80211_ops.set_monitor_channel`, gained an extra `struct net_device *dev` parameter upstream. The owner cites kernel commit `9c4f83092775`, which landed in mainline 6.13 and was backported to 6.12 stable from 6.12.101.
- The owner says Ubuntu cherry-picked it into its 24.04 `6.8.0-147` update, while the kernel keeps reporting version 6.8.x. So the driver's version checks pick the wrong prototype and the build fails with an incompatible pointer error.

## Why the first two fixes failed (per the owner's comments)

1. First fix (`70f3c63`): added a check on Ubuntu's ABI number but only when the kernel version equaled 6.8.0. The reporter's rebuild showed the same error. The owner then downloaded the real -147 header package and found it reports version 6.8.12, not 6.8.0.
2. Second fix (`8e334cd`): a version range. The owner says CI then broke, because Ubuntu 22.04's Azure kernel (6.8.0-1064-azure) reports the same version 6.8.12 and a higher ABI number, yet still uses the old prototype. So the two kernels look identical to a version check but need opposite code.
3. Third fix (`f5ba6c3`): stop checking version numbers. The code asks the compiler what type the callback field actually has and picks the matching wrapper. The owner says it builds a clean module against both real kernels' header packages, and CI is green.

## Status

The reporter will test the third fix on Monday. The owner says it is not done until confirmed on a real -147 machine. As of my check, no user has confirmed it.

## Why this was picked

It shows a pattern that hits other out-of-tree kernel drivers: distribution kernels backport API changes without changing version numbers, so version checks fail. The thread has a working-in-progress answer: ask the compiler.
